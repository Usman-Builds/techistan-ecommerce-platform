# Deploying the backend to Render

The image already builds and runs (`docker compose up` works end to end), so the container side of this is done. What follows is everything *around* it.

Companion file: [`render.yaml`](../../render.yaml), at the repo root.

---

## Before you start: three blockers

### 1. There is no repository covering the backend — but two nested ones exist

Render deploys from GitHub, GitLab or Bitbucket. Nothing here is deployable yet, and the starting position is more awkward than a bare directory:

| Path | State |
| --- | --- |
| `ecommerce/` | ~~no repo~~ — **resolved**: the repo is now rooted here, on `main`, and `render.yaml` sits at its root |
| `Code/frontend/user_client/` | its own repo: 2 commits, no remote, 61 uncommitted paths |
| `Code/frontend/admin_client/` | its own repo: 2 commits, no remote, 56 uncommitted paths |

Both frontend repos came from `create-next-app`, which runs `git init` for you. Neither has ever been pushed anywhere.

This matters because of what happens if you ignore it. Running `git init` at `Code/` and then `git add -A` does **not** add the frontends' files. Git sees a `.git` inside a `.git` and records each one as a *gitlink* — a bare commit pointer, like a submodule with no URL. Clone that repo and both frontend directories come out **empty**. The backend image would still build (its Docker context only reaches `backend/` and `shared/`), so you would not notice until you tried to deploy a frontend.

Decide this before the first commit:

**One repo for everything (recommended for a monorepo).** Absorb the frontends by removing their inner repos. Their history is 2 commits with no remote, so the loss is small — but it is a loss, so it is your call:

```bash
cd "D:/Work/Hobby Projects/ecommerce/Code"
rm -rf frontend/user_client/.git frontend/admin_client/.git   # discards that history
git init -b main
git add -A
git status          # <- READ THIS BEFORE COMMITTING
```

**Or keep them separate**, and give the backend its own repo at `Code/backend/`. Then `render.yaml` moves to `Code/backend/render.yaml` and its Docker paths become `./Dockerfile` and `.`, and every `COPY` in the Dockerfile loses its `backend/` prefix. This is now viable — the backend stopped reaching outside its own directory when `Code/shared` was split into per-app copies — but it is still more moving parts than the single repo.

Whichever you pick, before committing check that no `.env*` file except the two `.example` ones is staged. The three package-level `.gitignore` files cover `node_modules` and env files in their own subtrees, but nothing covers `Code/` itself. Then push to a new private GitHub repo.

> **This is what was done.** The repo is rooted at `ecommerce/`, not `Code/`, so `render.yaml` lives at `ecommerce/render.yaml` and its two Docker paths carry the `Code/` prefix: `dockerfilePath: ./Code/backend/Dockerfile` and `dockerContext: ./Code`. Setting the context to the repo root instead is a build failure, not a slow build — every `COPY` in the Dockerfile is written relative to `Code/`, and `.dockerignore` is read from the context root and lives at `Code/.dockerignore`.
>
> The gitlink warning above still stands: both frontend directories are recorded as bare commit pointers. That does not affect this backend deploy, but it will bite when you deploy a frontend.

### 2. You need two more accounts, not just Neon and Cloudinary

`config/validation.ts` refuses to boot on `NODE_ENV=production` without all of these. Neon and Cloudinary cover two of the four external dependencies. The missing ones:

| Service | Variable(s) | Why it is mandatory |
| --- | --- | --- |
| **Stripe** | `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Checkout. Test-mode keys satisfy the validator if you are not selling yet. |
| **Resend** | `RESEND_API_KEY` | Verification, password reset, order confirmation emails. Needs a verified sending domain. |

Everything else is either generated by Render or a URL you decide.

### 3. Login cookies across two different hosts (handled by the clients)

`auth.controller.ts` sets the JWT cookies with `sameSite: 'lax'` and no `domain`. Two different `*.onrender.com` (or `*.vercel.app`) hosts are **different sites**, because both are public suffixes. If the browser called this API directly from a client on another host, it would drop those cookies. Login would appear to succeed, then every request, including `/auth/refresh`, would return 401.

Both Next.js clients avoid this. The browser calls the client's own `/api/*`, and the client's `next.config.ts` rewrites that to `NEXT_PUBLIC_API_URL`. The cookies are then first-party on the client's host, where `proxy.ts` and server components can also read them. No backend change is needed. When deploying a client:

- Set `NEXT_PUBLIC_API_URL` to this service's URL **before it builds**. It is baked in at build time, so changing it later needs a redeploy.
- Each client keeps its own session: logging into the admin console does not log you into the storefront.
- CORS no longer matters for browser traffic.
- A custom domain (`api.techistan.com`, etc.) is still nicer, since it gives a stable Stripe webhook URL, but login no longer depends on one.

## Deploy

### Step 1 — Push, then create the Blueprint

In Render: **New → Blueprint**, pick the repo, and it will read `render.yaml`. It creates one web service, `techistan-api`, in **Ohio** — deliberately the same region as your Neon project in `us-east-2`. That matters: the connection test measured ~233 ms per query from here, and essentially all of that is distance. Same region takes it to single digits.

### Step 2 — Fill in the secrets

Render prompts for every variable marked `sync: false`. The four JWT/cart/cron secrets are generated for you.

`DATABASE_URL` — use the **pooled** Neon host (the one containing `-pooler`), exactly as you tested it:

```
postgresql://USER:PASSWORD@ep-....-pooler.c-5.us-east-2.aws.neon.tech/neondb?sslmode=require&channel_binding=require
```

The URL variables depend on where the clients end up:

| Variable | Example |
| --- | --- |
| `USER_APP_URL` | `https://techistan.com` |
| `ADMIN_APP_URL` | `https://admin.techistan.com` |
| `CLIENT_ORIGINS` | `https://techistan.com,https://admin.techistan.com` |

No trailing slashes in `CLIENT_ORIGINS` — it is compared to the browser's `Origin` header verbatim.

**`ADMIN_PASSWORD`: generate a new one.** Do not reuse the dev value from `.env.development`. It is a preseeded `SUPER_ADMIN` on a database that is about to be reachable from the internet.

```bash
openssl rand -base64 24
```

### Step 3 — Run the migrations yourself

The Neon database is currently **empty — zero tables**. Nothing creates them for you:

- `preDeployCommand` requires a paid instance type ([Render docs](https://render.com/docs/free)).
- The runtime image has the Prisma CLI stripped out to save 50 MB, so there is nothing to run even if you added a start-time hook.
- Free instances have no shell.

So run it from your machine, once, against the **direct** host — not the pooler. Migrations take advisory locks that a transaction-mode pooler cannot hold across statements:

```bash
cd "D:/Work/Hobby Projects/ecommerce/Code/backend"

# direct host = the pooled host with "-pooler" removed
DATABASE_URL='postgresql://USER:PASSWORD@ep-....c-5.us-east-2.aws.neon.tech/neondb?sslmode=require' \
  npx prisma migrate deploy

DATABASE_URL='...same direct URL...' npm run seed
```

That applies all 14 migrations and creates the admin user, store settings and starter catalog. Repeat the `migrate deploy` line after any future schema change, before the deploy that needs it.

> On a paid plan you can move this into the platform: uncomment `preDeployCommand` in `render.yaml` **and** drop `node_modules/prisma` from the `rm -rf` line in the `prod-deps` stage of the Dockerfile, so the CLI survives into the runtime image.

### Step 4 — Point the third parties at the deployed URL

Only possible once you know the service's public URL.

- **Stripe Dashboard** → Developers → Webhooks → add endpoint `https://<your-api>/payments/webhook`. It shows a `whsec_...` — that is `STRIPE_WEBHOOK_SECRET`. It is **not** the same secret `stripe listen` prints locally; those are per-endpoint.
- **Resend** → verify your sending domain, then set `EMAIL_FROM` to an address on it.

### Step 5 — Check it

```bash
curl https://<your-api>/health      # {"status":"ok"}
```

Then log into the admin client with `ADMIN_EMAIL` / `ADMIN_PASSWORD` — that exercises the database, JWT signing and the cookie path in one go, which is where problem 3 above will show up if it is going to.

## What you do *not* need

- **Object storage on Render.** Cloudinary covers it, and the app never writes to disk — I checked; there are no `writeFileSync`/`createWriteStream` calls, and the PDF and CSV exports stream straight to the response. So Render's ephemeral filesystem is fine and you do not need a paid persistent disk.
- **Redis.** Nothing uses it. The rate limiter is in-memory, which is correct for a single instance. If you ever scale past one, the limits become per-instance and you would want a shared store.
- **A Render Postgres.** Neon is your database.

## Free-plan realities

**Spin-down.** After 15 minutes without traffic the service stops, and the next request waits ~1 minute for it to come back. Neon's free tier also auto-suspends after ~5 minutes idle. Stacked, the first visit after a quiet night is slow enough that people assume the site is broken.

**Scheduled jobs stop with it.** The abandoned-cart recovery runs in-process via `@Cron`. A spun-down service runs nothing. There are already guarded `POST /cron/*` routes for exactly this — point a free external scheduler (cron-job.org and similar) at them with the `CRON_SECRET` as a bearer token. That runs the jobs *and* keeps the service warm, which fixes both problems with one setting.

**Memory.** Free gives 512 MB. Nest with this many modules plus the Prisma engine typically sits around 250–350 MB, so it fits — but not with much room. If deploys start dying with exit code 137, that is the OOM killer, not your code.

## If the deploy fails

| Symptom | Cause |
| --- | --- |
| `no open ports detected` | Something set `PORT` explicitly and overrode Render's. Remove it — the app already reads Render's. |
| `Config validation error: "X" is not allowed to be empty` | A `sync: false` variable was left blank. Joi lists every offender at once. |
| `Can't reach database server` | `DATABASE_URL` typo, or you used the direct host where the pooled one belongs. |
| Login returns 401 on every request after a successful login | The SameSite problem. See blocker 3. |
| Checkout sits on "Payment processing…" | Stripe has no webhook endpoint for this API, or `STRIPE_WEBHOOK_SECRET` is not that endpoint's `whsec_...`. See Step 4. The order page settles the payment from Stripe's API as a fallback, but only while someone has it open, so the webhook is still what confirms everything else. |
| Build fails at `gen:brand` | The build context is wrong. It must be the repo root, not `backend/`. |
